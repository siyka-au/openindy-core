# Plugin ABI and supported toolchains

A plugin is a shared library loaded into the host process. The plugin interface
(`include/plugin/`) passes `std::string`, `std::vector`, `std::unique_ptr` and so
on across that boundary and is called through virtual tables, so host and plugin
must agree on the binary layout of the C++ standard library and of the
compiler's C++ ABI. This is a real constraint, not a formality: a mismatch
loads fine and then corrupts memory.

## Supported matrix

Linux x86_64 is the only supported platform today. Windows (MinGW **or** MSVC,
never mixed within one build) would be added if a user base appears; nothing is
designed for it beyond leaving room in the toolchain string.

A plugin and the host it is loaded into must share:

| Must match | Notes |
| --- | --- |
| OS | Linux plugins load into Linux hosts only. |
| Compiler family and standard library | In practice libstdc++ with GCC or clang (both Itanium C++ ABI). libc++ and libstdc++ are mutually incompatible. |
| Architecture and pointer width | x86_64 with x86_64, and so on. |
| `kPluginAbiVersion` | Hand-declared in `include/plugin/plugin_abi.h`; see `abi/README.md`. |

Rules of thumb:

- **GCC and clang with libstdc++ on Linux are compatible** (same Itanium ABI,
  same standard library). The compiler *name* is not compared.
- **libstdc++ is backward compatible**: a plugin built with the oldest supported
  GCC loads on a host whose libstdc++ runtime is newer, but not the other way
  round (a plugin built with a newer GCC may need symbols an older runtime lacks;
  the dynamic loader then fails, or worse). So: build plugins you distribute with
  the oldest supported GCC (the CI floor, GCC 14, see below). The compiler
  *version* is therefore deliberately not part of the compared string.
- **Flags that change layout break compatibility** and cannot be detected at
  load time: `-D_GLIBCXX_USE_CXX11_ABI=0` (the old string ABI), `-fno-rtti`,
  sanitizers (an ASAN host with a non-ASAN plugin, or the reverse, is not
  supported; the sanitizer CI builds everything under test with the sanitizer),
  `-fabi-version=` differences, and a different `-std` when it changes the
  layout of types in the headers.
- **MSVC, MinGW and Linux toolchains are mutually incompatible.**

## The toolchain string

Every plugin exports `const char* oi_plugin_toolchain()` (generated by
`OI_DECLARE_PLUGIN*`), built at compile time by
[`include/plugin/toolchain.h`](../include/plugin/toolchain.h):

```
<c++ abi>-<standard library>-<os>-<architecture>
itanium-libstdc++-linux-x86_64        (GCC or clang with libstdc++ on Linux)
msvc-msvc-stl-windows-x86_64          (reserved shape for MSVC; not supported yet)
```

`oi::PluginLoader` compares the plugin's string with its own compile-time value
after the ABI version check and before `oi_plugin_create`. A mismatch is
refused with `PluginLoadStatus::kToolchainMismatch` and an error naming both
strings; a plugin without the symbol is refused like a missing entry point
(`kMissingEntryPoint`). The compiler name (`gcc`, `clang`, `mingw`, `msvc`) is
available as `oi::kToolchainCompiler` and is reported in the plugin metadata's
`compiler` field for diagnostics only (the plugins' CMake and
`OiMetaData::getCompiler()` use the same words).

`toolchain.h` also `static_assert`s that the architecture agrees with
`sizeof(void*)` and that the target is little endian. For tests,
`-DOI_TOOLCHAIN_OVERRIDE="..."` replaces the whole string in one translation
unit.

## Compiler baseline (CI)

GCC 14 is the floor: Debian 13 ships it, Ubuntu 24.04 / Linux Mint 22 can install
`g++-14`, and it has the C++23 library features the code uses (`std::expected`,
`std::format`, `<stop_token>`/`std::jthread`, ...). CI builds and tests with GCC
14, 15 and 16; the plugin ABI baseline (`abi/baseline.abi`) is generated with
GCC 14. A GCC 13 build runs as an informational, allowed-to-fail job so that it is
known whether the floor could be lowered.
